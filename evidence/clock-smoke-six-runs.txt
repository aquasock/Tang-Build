VALIDITY CHECK: IS THE CAPTURE LIVE?
  Byte-identical files across six runs is exactly what a wedged buffer looks
  like, so the same running design was captured for 60 s instead of 30:
    122 lines in 60.0 s, n = 0x0038 .. 0x00b1, all d(n) = 1,
    d(c27) = 2211 or 2212 throughout.
  A stale buffer would have returned the same 44 lines again.  It returned
  122, so the data is live and the six runs above are six real measurements.

AND A SECOND ANOMALY, RECORDED RATHER THAN RESOLVED
  The 60 s capture runs at 2.02 lines/s; the six 30 s runs ran at 1.43
  lines/s.  d(c27) per line is 2211.8 in both, i.e. each line carries
  0.5400 x 2^25 clk27 cycles.  If a line really is 2^25 sys_clk cycles, the
  line rate cannot change -- so either the cadence is not 2^25 cycles in the
  implementation, or the line rate is not stable, and which of the two is
  not known.  It does not touch the ratio result, which compares two
  bitstreams measured under the same conditions, but it does mean the
  absolute frequencies rest on assumptions and should not be quoted as fact:
    - the UART anchor assumes the design's baud is exactly 115200,
    - the ratio assumes the cadence is exactly 2^25 sys_clk cycles.
  Note also that the board's behaviour appears to drift while left running,
  which is consistent with the load and configuration trouble found in
  entry 8.  The board was left running variant B in SRAM.

  One correction to entry 7's framing: the ~3.9% disagreement it noted
  between the cadence and the UART anchors is an artefact of the decoder
  dividing the whole capture window by the number of line intervals.  The
  window opens before the first line arrives, so its dead time is counted
  as if it were line periods and the cadence anchor reads low.  It is not a
  discrepancy in the design.
