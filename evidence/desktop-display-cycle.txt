# CORRECTED 2026-10-09: THE CLOCK RATES IN THIS FILE ARE TWICE THEIR TRUE VALUE.
# tools/decode-clock-smoke.py multiplied the edge count by 8192, on the reading that
# an edge count is a cycle count.  It is not: bit 12 has a period of 8192 cycles and
# yields TWO edges per period, so the factor is 4096.  Every rate below is 2x high and
# every "doubled" conclusion drawn from them is an artefact of that script.  The edge
# counts themselves are sound and are what the correction was derived from.  See
# evidence/clock-smoke-panel.txt and core-log entry 30.
#
# In particular the reading that ODIV0_SEL must be doubled INVERTS: the field is a
# straight divisor, so 50 divides by 50 -- which is what the design asks for -- and
# ODIV0_SEL=100 halves the output to 13.5 MHz.  Any workaround that changed 50 to 100
# on the strength of these numbers is a 2x error.  See core-log entry 30.
# MEASURED 2026-10-09: ODIV0_SEL=100 does halve the output on silicon, so that
# workaround puts this core's hclk5 at 185.625 MHz instead of 371.25 -- half the
# TMDS bit clock.  See evidence/clock-smoke-sweep.txt section 5.  It is in the
# bitstream loaded on 2026-10-09.
#
# desktop core: packing it, and why the display is still dark

## 1. The flow fix -- string parameters from the slang front end

The desktop core could not pack at all.  Cause, measured by comparing the
two netlists' pll_27 PLL cells:

                  clock-smoke (packs)   desktop (failed)
  FCLKIN          50                    0011010100110000      <- ASCII '50'
  CLKOUT0_EN      TRUE                  01010100010100100101010101000101  <- 'TRUE'
  CLKFB_SEL       INTERNAL              0100100101001110...   <- 'INTERNAL'
  MDIV_SEL/ODIV0_SEL   binary           binary                (same both)

read_slang keeps a Verilog *string* parameter as a bit vector where
read_verilog keeps it a string.  gowin_pack wants the strings: float() on
the first gives 1.1e13 (the exception text 11010100110000.0 is that,
leading zeros stripped) and the second raises KeyError in pll_attrvals.

The fix in scripts/synth-desktop.sh converts them back.  It is scoped to
PLL-family cells, and that scope is load-bearing: a first attempt applied
the 'does this decode to printable text' test to the whole netlist and would
have converted 536 parameters, including LUT INIT values --
desktop_sockets.hs_LUT4_I1.INIT = '_3'.  It would have silently corrupted
the design's lookup tables.  It did not run, which was luck.  PLL numeric
fields are 32-bit, so a realistic divider leaves its high bytes 0x00 and
cannot decode as text; that is why the scope makes it safe.

Result: 'PLL string parameters restored (129)' -- 43 x 3 PLLs, exactly the
string set the library declares.

## 2. The packer fix -- LSRIMUX_0 on an output serialiser

GW5AST_138C.get_out_iologic_attrs added the fast-clock selection and the
OSER16 aux attributes but never removed LSRIMUX_0.  LSRIMUX belongs to the
INPUT half (against the output's LSROMUX), so an output cell carrying it
spends a fuse the vendor does not -- 'LSRIMUX_0 ours set, theirs clear, one
fuse per tile', the only difference this project ever found between our
bitstream and the vendor's working one, and it is at the TMDS tiles, which
are OSER10s.  Fixed by dropping that attribute on the output path.

Re-packing moved 14 bits of 35.7M, every cluster 0 -> 1, in the TMDS region:
  [34633209] 0->1   [34633233] 0->1   [34633834] 0->1   [34634646..647] 00->11
  plus the checksum tail.  Fuses we were spending, cleared.

## 3. Hardware

Three loads of /tmp/tb/desktop-lsrimux.fs (35,752,331 B, sha256 ec6baf2a...),
each after a power cycle so the load takes (a load without one does not).
  load 1  monitor: same as before, flash splash then dark, screen sleeps
  load 2  monitor: same, user watched the transition closely
  load 3  a different, better monitor: 'no signal right away', went to sleep,
          and two quick flashes seen after the load

The two flashes are the JTAG reconfigure releasing and settling, not video.
'No signal' from a monitor that distinguishes it from 'out of range' means
NO TMDS CLOCK AT ALL -- not timings it cannot use, but nothing.

## 4. What the day ruled out

  - the pixel clock.  The committed build runs it at 148.5 MHz (the doubled
    divider) and this build at 74.25; both give no signal.
  - the serialiser fuses, now that LSRIMUX_0 is cleared.
  - the placement.  Our routed build has div5 at X181Y81/CLKDIV_3 (block 3,
    not the dead blocks 0/1), the three PLLs on the reference sites X0Y45,
    X1Y81, X32Y108, and the OSER10s at X181Y102/100/57 -- the vendor's own.
  - the CLKDIV and its lane: clock-smoke measured hclk at 74.2452 MHz from
    that exact site.

## 5. Also established this cycle

  Gowin's IP Generator record beside the wrapper (src/pll/gowin_pll_27.ipc)
  settles the ODIV question: ClkinClockFrequency=50,
  ClkfboutVCODivideFactorStatic=27, Clkout0VCODivideFactorStatic=50,
  Clkout0ExpectedFrequency=27.  ODIV0_SEL = 50 means divide-by-50.

  The ODIV field occupies 48 bits in six groups of eight at a 1,584-bit
  stride -- six tiles of the PLL site -- and is not a positional binary
  divide: a sweep over ODIV0_SEL = 4, 8, 16, 32, 64, 100 gave seven distinct
  bitstreams with the groups behaving like a coarse cascade plus a fine value.

  The packer's rejection of ODIV0_SEL = 100 on the desktop IP was not about
  the divider: get_pll_attrvals does float() on A_FCLKIN, which is the cell's
  FCLKIN verbatim, and the slang front end had made it the ASCII of '50'.
  Fixed in the flow (section 1), not by making the packer lenient.

## 6. Open

  - the display is still dark.
  - the packer's divider scaling is unfixed: the requested ODIV still means
    half to the hardware for the values measured.  ODIV0_SEL = 100 is a
    workaround in the RTL, not a correction.
  - why no TMDS clock is emitted is not known.  The desktop core has no
    readout, so its clocks cannot be measured; the next instrument is to put
    the display chain into clock-smoke, which reports over the board's own
    proven UART, and see whether a monitor syncs to that.
  - scripts/pnr-desktop.sh needs fixing: it takes whatever
    nextpnr-himbaechel is first on PATH (the suite's, which has no placeable
    PLL bel), needs SYNTH_DESKTOP_NO_ENV and the suite environment sourced,
    and needs the three INS_LOC PLL pins.
  - the fork's gowin_pack.py fix is a change in the apicula fork, not in
    this repository.

## 7. Added after the LED panel was validated (same day, later)

Two results, one negative and one a correction.

**No dead FSM, and that branch is closed.**  The synthesis log of the tree that
built the core already on disk extracts four state machines --
`keyboard_link`, `keyboard_link2`, `sys_inst.desktop_endpoint.state` and
`sys_inst.fdd_state` -- and yosys re-encodes all four one-hot, which is exactly
the shape that killed the clock-smoke heartbeat.  But every one of them carries a
`<RESET STATE>` in its state encoding and the first input of each is
`sys_resetn`, so they power up in a valid one-hot code.  The hazard is one-hot
*without* a reset, and the core has none.  Recorded because a display pipeline is
precisely where a dead FSM would have hidden: if the display is dark, it is not
this.

**The `ODIV0_SEL` workaround is reverted.**  The tree that last built the core
(`TinyTang/build/desktop/reconstruct.jhpQys`, the tree `source-path.txt` names)
had `ODIV0_SEL = 100` in `src/pll/gowin_pll_27.v`; it is back to 50, and that
file is now unmodified against upstream, so the workaround was its only edit
there.  The direction is settled by measurement rather than by the banner:
clock-smoke at `ODIV0_SEL = 50` reads `clk27` at 0.5400 x sys_clk = 27.0 MHz,
which is what the design asks for, and at 100 reads 13.5 MHz.  The field divides
as requested, so no packer fix is needed, and the bullet below -- "the requested
ODIV still means half to the hardware" -- is superseded: what meant half was the
decoder.  **The core has not been rebuilt since, so the bitstream loaded on
2026-10-09 still carries 100**, and its `hclk5` is still 185.625 MHz rather than
371.25 -- half the TMDS bit clock.

**A durability warning beside both.**  The tree's own git diff is nine files and
662 insertions -- the HDMI, packet-picker, nes2hdmi, iosys and OLED work -- and
it lives as *uncommitted changes in a scratch build directory with a random
suffix*.  Nothing in this repository carries it.  If that directory is cleaned,
the desktop work goes with it, and the `ODIV0_SEL` revert just made would go with
it too.  It wants a patch in this repository, the way `patches/0001` and `0002`
already capture edits made outside it.

## 8. The cheap test: both fixes exonerated (same day, later)

The two fixes carried by this build were the lane selection and the `pll_27`
divider.  Both are now on the board and the display is still dark, which
retires both as causes.

**Built through the documented pipeline.**  `scripts/synth-desktop.sh` on the
working tree gives `nestang-top-open.json`, 7,689,984 bytes, with the census the
project expects -- `CLKDIV 1`, `OSER10 3`, `ELVDS_OBUF 4`, `DPB 10`, `ALU 1096`.
`scripts/pnr-desktop.sh` routes it with 0 errors.  Packing with the fork's
apycula and no `*_as_gpio` options gives `.fs` sha256
`882222d6ece66f0256f89ae10ba978e4d63e60bddba887f34d9acf198fc288e1`, 35,752,331
bytes.

**Offline acceptance, before loading.**  `iol-state.py` decodes the IOLOGIC
attribute set from the packed bitstream, and the three serialisers read:

```
previously loaded build   CLKOMUX 61, OUTMODE 16, WRFCLKSEL 102            (3)
this build                CLKOMUX 61, FCLKSEL1 81, FCLKSEL2 114,
                          LSRIMUX_0 1, LSROMUX_0 1, OUTMODE 16, WRFCLKSEL 102  (7)
vendor's working build    CLKOMUX 61, FCLKSEL0 79, FCLKSEL1 81, FCLKSEL2 114,
                          FCLKSEL3 86, HWL 107, LSRIMUX_0 1, LSROMUX_0 1,
                          OUTMODE 16, WRFCLKSEL 102                        (10)
```

So the lane selection is genuinely in the bitstream now, on all three
serialisers, where the loaded build had none -- the build FINDINGS section 7
describes as ready but never loaded.  The remaining difference from the vendor
is the one already recorded as not a cause: they carry four `FCLKSEL` values and
`HWL`, we carry two, and the decoder aliases `FCLKSEL` values onto the same
fuses.

**On the board.**  The core loads and is alive: UART1 at 2 Mbaud returns a steady
twelve-byte keylink frame, `FC 00 09 08 00 00 00 00 00 00 00 00`, about four
times a second.  So the system clock path, the fabric and the UART all work.
The display is still dark, and the brief flash the monitor gives at load time is
identical to before, so it is the monitor reacting to configuration and carries
no information.

**What that retires.**  The lane constraint is not sufficient: with a lane
selection present at all three serialisers the display is still dark.  The 2x
clock defect is not the cause: with `pll_27` at the vendor's own 27 MHz and
`hclk5` at the full 371.25 MHz rather than half, the display is still dark.
Neither is a dead FSM (section 7).  The open branches are the two FINDINGS
section 7 named: the fuses at the three TMDS tiles, compared against the
vendor's, which is offline work with the unpacker; and whether the display
clocks are actually running on silicon, which no offline check can answer and
which needs the readout the core does not have.

**Flow gotcha, recorded so it is not re-derived.**  `scripts/pnr-desktop.sh`
passes nextpnr no `*_as_gpio` options, so the packer has to be run without them
too: passing the vendor's six (`mspi`, `ready`, `done`, `i2c`, `cpu`, `sspi`)
makes `gowin_pack` refuse with "i2c_as_gpio has conflicting settings in nexpnr
and gowin_pack", which is the packer working correctly.  Matching the vendor's
pinout would mean passing the options to both tools, and the flow does not do
that today.
