Clock monitor (core-log entry 57's instrument) -- build and off-board evidence
2026-10-10T09:50-07:00

Purpose
-------
Give the agent senses inside the fabric so the desktop core's clocks can be
measured on silicon rather than inferred from the timing model.  Entry 57 chose
cycle counters: no processor, no accelerator.  This file records what was
built, what was verified off the board, and the two repository defects the work
uncovered.  The on-silicon readback is not in this file -- it is the remaining
step and needs the board.

The instrument
--------------
fpga/desktop/clock_monitor.sv, instantiated by fpga/desktop/desktop_regs.sv,
readable over the desktop register endpoint's read32 (frame type 0x10,
opcode 1), which already existed:

    0x120  clk_a    `clk` cycles, probe A   (read directly; clk is the read domain)
    0x124  clk_b    `clk` cycles, probe B
    0x128  pix_a    `hclk` cycles, probe A  (gray-synced into clk)
    0x12c  pix_b    `hclk` cycles, probe B
    0x130  ref_a    `sys_clk` (50 MHz crystal) cycles, gray-synced
    0x134  4d4f4e31  "MON1" stamp

Design choices, each for a reason: free-running so no reset net is added; gray
code on the two cross-domain counters because a binary counter sampled mid-carry
would hand the synchroniser a mixture (gray changes one bit per increment, so
the two-flop capture is old-or-new); two probes per fabric-routed clock so a
region the route failed to reach shows as a counter that stands still; and the
50 MHz crystal as the only absolute reference.  Nothing is pinned -- the placer
chooses where the probes land, per the operator's instruction.

Off-board verification (tools/tests/test_desktop_core.sh, verilator)
------------------------------------------------------------------
The desktop core's own regression suite now exercises the monitor against the
bench's three clocks -- 46.53 ns (21.492 MHz), 13.468 ns (74.25 MHz) and 20 ns
(50 MHz) -- using the reference counter as the timebase:

    clock monitor: clk=452041/ref=1051671 pix=1561740/ref=1051671 probes agree PASS
    desktop UART: 56 register responses, ID, keyboard traffic and layer enable PASS
    desktop responses: independent Python CRC check PASS
    desktop video: VGA 1237500 raster pixels, HDMI 921600 visible pixels; no left-edge leak PASS
    desktop core: reconstruction and affected regressions PASS

  clk   452041/1051671 = 0.42984 = 21.492/50   (clk measured at 21.492 MHz)
  pix  1561740/1051671 = 1.48501 = 74.25/50    (pixel measured at 74.25 MHz)

Both probe pairs agree within 1%.  This is simulation, not the board: it proves
the register map, the frame, the gray crossing and the arithmetic, and nothing
about silicon.  The band in the bench is +/-1%, which absorbs the few hundred
microseconds the sequential reads take.

The firmware's request encoder was checked against the project's own
independently-computed vector: tools/tests/fpga_ext_frame_test.cpp expects
CRC bytes 73 17 for command 0x10 and payload
01 02 10 02 00 00 00 20 12 34 56 78; the C implementation in
ports/bl616/tang_fpga_uart.c reproduces 7317 exactly.

Host side
---------
ports/bl616/tang_fpga_uart.c, TinyTang firmware:

    fpgar <hex-addr>   read one desktop register over UART1 (read32)
    fmon  [hold-ms]    read all five counters twice, print deltas and rates in Hz

Firmware image: build/build_out/tinytang_bl616.bin, sha256 4d7051da...
The pre-monitor firmware of this tree is e2205009...; the two commands are the
only change.

Defect 1 -- the committed CST cannot rebuild the working baseline
----------------------------------------------------------------
The baseline the board has been running (build/vga-diagnostic/baseline,
7b95d942...) was built with three placement-macro pins that exist only in the
preserved build artefacts -- build/vga-diagnostic/baseline/cst.cst and
build/desktop/reconstruct.jhpQys/src/desktop/desktop.cst:

    INS_LOC "pll_27.PLL_inst"   PLL_L[1];
    INS_LOC "pll_hdmi.PLL_inst" PLL_L[3];
    INS_LOC "pll_nes.PLL_inst"  PLL_R[0];

TinyTang/fpga/desktop/desktop.cst has none of them.  Without the pin the open
flow produces no violation-free placement: a clean eight-seed sweep
(7,11,13,17,19,23,29,31) gave zero clean seeds and seeds 23 and 29 did not even
route (`Net hclk5 has no route to the FCLK of u_hdmi.hdmi.serializer.gwSer0`).
With pll_nes at PLL_R[0] the monitor build has clean seeds 17 and 19.  Same
engine: nextpnr 2026-10-09 08:26 and apicula 4281068 both predate the baseline.
The baseline's own pnr-input.json is 8,510 cells against today's 8,585, so the
netlist drifted ~75 cells as well.  **Fixed on the operator's instruction:** the
three `INS_LOC` pins now live in `TinyTang/fpga/desktop/desktop.cst`, and a
fresh reconstruct + build at seed 17 with no `PNR_CST` override reproduces
`desktop.90d3fa3a84fa.bin` / `desktop.1e465857f24d.fs` byte for byte, so this
repository can again rebuild its own working core.  Note that the pin is a
*placement* choice, not a repair: all 1199 `clk` fabric fallbacks remain.

Defect 2 -- scripts/build-desktop-core.sh's clock override was dead code
-----------------------------------------------------------------------
Gate 2c ran `python3 tools/clock-route-inventory.py ...` as a bare command under
`set -e` on line 31, then read `$?` on the next line.  A regressed topology made
the inventory exit 1 and the shell abort before the exit code was read, so
ALLOW_UNVERIFIED_CLOCK -- the documented way to pack an experimental bitstream --
could never be reached.  Fixed by wrapping the invocation in `if`, which is the
smallest change that makes the code do what its comment says.  With the fix the
override works and the build above was produced.

What gate 2c said, and why it is not a surprise
-----------------------------------------------
    CLOCK TOPOLOGY REGRESSED: clk: fabric fallbacks 943 -> 1199

256 more, and the monitor adds exactly 256 clk-domain flops (64 counter + 192
synchroniser).  Every one rides fabric, which is the chipdb gap entry 55/56
describe stated back as a measurement: adding load to `clk` adds fabric
fallbacks one for one.  The build is therefore labelled experimental -- the
label is about the clock topology, not the timing, which is clean.

On silicon -- the measurement
----------------------------
Firmware `4d7051da...` was flashed with `tools/tinytang_flash.py` and the board
power-cycled, after which `fpgar` validated the readback against the baseline
core's own registers before the monitor core was loaded:

    fpgar 0    -> 0x00544453 status 0     (magic)
    fpgar 4    -> 0x00010001 status 0     (ABI 1.1)
    fpgar 100  -> 0x00180010 status 0     (fixed 24 x 16)
    fpgar 134  -> 0x00000000 status 4     (no monitor in the baseline -- correct)

Then `tangload /cores/console138k/desktop-monitor.90d3fa3a84fa.bin` reported
`core loaded`, `fpgar 134` returned `0x4d4f4e31` status 0, and `fmon` was run
three times.  Repeated measurements agree:

    run 1  hold 10004 ms   clk 21503792 Hz  clk_b 21505312  pix 74249947  pix_b 74249948
    run 2  hold  8005 ms   clk 21504984 Hz  clk_b 21505311  pix 74250045  pix_b 74249975
    run 3  hold  8004 ms   clk 21503783 Hz  clk_b 21505322  pix 74250022  pix_b 74250032

  clk   measured 21.504-21.505 MHz   constrained 21.49 MHz   ratio to ref 0.43007
  pix   measured 74.2499-74.2500 MHz  intended 74.25 MHz      ratio to ref 1.48500
  ref   500,235,740 cycles in 10,004 ms -> 50.0036 MHz (the crystal, nominal 50)

Both probes agree to about 0.007% on both clocks, and the counters were seen to
wrap mid-measurement (`ref 4260395265 -> 365666368` gave the correct delta), so
the 32-bit wraparound path is exercised rather than assumed.

Two readings are worth stating plainly.  First, **the clocks are at their
intended rates on silicon in an open-flow-built desktop core**, which is the
question entry 57 asked and the one the timing model could not answer; the model
is pessimistic about *skew*, not about rate.  Second, `clk` measures ~21.505 MHz
and not the 21.492 MHz the SDC names, which is not an error: the design's own
PLL divides a 2000 MHz VCO by 93, so ~21.505 MHz is the frequency the part
actually produces, and the constraint is the conservative one.

`oled_frames` (0x108) and `oled_signature` (0x10c) both read 0 in this
configuration, where VGA is on the PMOD and the OLED panel is not in play; the
reading is recorded but establishes nothing either way about the screen.

The user's report, and what it changes
-------------------------------------
The user reports a **perfect VGA image** with this core loaded, at the console
prompt.  The bitstream was confirmed before the observation was attributed: the
running core answers the monitor's stamp (`fpgar 134` -> `0x4d4f4e31`, status
0) and the desktop magic (`fpgar 0` -> `0x00544453`), so the image is
`desktop.90d3fa3a84fa.bin` and not the baseline.

That overturns the standing conclusion.  Entry 55 closed the vertical-line
investigation with "there is no clean placement to sweep for -- only dead or
lined", because every timing-clean configuration found was the lined baseline.
This build is timing-clean too (setup 0, hold 0) and renders perfectly, so the
lines are **placement-dependent, and a good placement exists**: the same
current source that is lined at the baseline's placement is clean at seed 17
with `pll_nes` at `PLL_R[0]`.

It also needs no new mechanism to explain it, only the one already measured.
The same build's clocks were read back on silicon as correct (21.504 MHz `clk`,
74.250 MHz `hclk`), so clock *rate* was never the lines' cause; what differs
between the two clean placements is skew.  This placement routes `clk` at
4.077 ns over 1199 sinks where the baseline's own evidentiary record carries
4.389 ns -- suggestive of the lever, but measured on a netlist about 75 cells
different, so it is a lead and not a controlled comparison.

Caveats, stated because this project has paid for assuming stability before: a
single session's observation is not a stability result, and entry 55's own
standard was four power cycles before calling a display good.  Stability is
unconfirmed and repeat power cycles are the next evidence.  The root cause is
untouched: 1199 `clk` fabric fallbacks remain, 256 more than the baseline, and
what changed is only that this placement's consequence for the picture is
invisible.


Power-cycle stability of desktop.90d3fa3a84fa.bin
----------------------------------------------
`/cores/console138k/desktop.bin` was set to `desktop.90d3fa3a84fa.bin` so
`/scripts/boot.tdsh` (which does `CORE=/cores/console138k/desktop.bin` then
`tangload "$CORE"`) boots the monitor core.  Each boot is tied to the bitstream
by repeated reads of the stamp, not assumed, because a single console read is
not evidence on this link.  The standard is entry 55's: four power cycles.

          fpgar 134 -> 0x4d4f4e31 status 0   (twice)
          fpgar 0   -> 0x00544453 status 0   fpga: core 84 at 2 Mbaud
          fmon 5000: clk 21502050 / clk_b 21505305 Hz, pix 74250066 / pix_b 74249954 Hz

  boot 2  2026-10-10T10:22  user: "pass"
          fpgar 134 -> 0x4d4f4e31 status 0   (twice)
          fpgar 0   -> 0x00544453 status 0   fpga: core 84 at 2 Mbaud
          fmon 5000: clk 21502762 / clk_b 21505283 Hz, pix 74249955 / pix_b 74249966 Hz

  boot 3  2026-10-10T10:30  user: "pass"
          fpgar 134 -> 0x4d4f4e31 status 0   (twice)
          fpgar 0   -> 0x00544453 status 0   fpga: core 84 at 2 Mbaud
          fmon 5000: clk 21503028 / clk_b 21505249 Hz, pix 74249993 / pix_b 74249956 Hz

  boot 4  2026-10-10T10:38  user: "pass"
          fpgar 134 -> 0x4d4f4e31 status 0   (twice)
          fpgar 0   -> 0x00544453 status 0   fpga: core 84 at 2 Mbaud
          fmon 5000: clk 21503067 / clk_b 21505265 Hz, pix 74249606 / pix_b 74249966 Hz

Result: four of four boots rendered perfectly, and every boot was tied to the
same bitstream by two independent reads of the monitor stamp rather than
identified by file size -- the practice the project adopted after `7b95d942`
and `67e8d724` turned out to be the same byte count.  Across all four boots the
measured clocks never moved outside 21.5020-21.5053 MHz for `clk` and
74.2496-74.2501 MHz for `hclk`, both probes agreeing inside 0.02 percent, so the
image is stable across the power cycles tested and not a lucky session.

Limits, stated because four boots is a bar and not a proof: four boots on one
board with one monitor; it says nothing about other placements, other boards or
a cold board, and it does not explain *why* this placement renders where the
lined baseline does not -- the skew measurement above weakens the obvious
answer rather than confirming it.  The seed-19 discriminator
(`desktop.aa6b0f9d733b.bin`, timing-clean, clk skew 4.657 ns) is built and not
yet run.

The first attempt before this is recorded rather than dropped: a power cycle
with the *lined baseline* still as `desktop.bin` booted that baseline, which
`fpgar 134` reported as status 4, so it was a test of the wrong image and not a
stability failure.

Is clk skew the discriminator?  Measured, and the answer is "not on its own"
---------------------------------------------------------------------------
The second clean placement was measured so the skew lead in entry 59 could be
tested rather than assumed.  Same tool (`tools/clock-skew-report.py` as the
nextpnr post-route hook), same netlist, same pinned PLLs:

  seed 17   clk 1199 sinks  1.549 .. 6.206   skew 4.077 ns   perfect image (user, boots 1-2)
  seed 19   clk 1199 sinks  1.549 .. 6.206   skew 4.657 ns   clean timing, display not yet seen
  baseline  clk               (entry 53)     skew 4.389 ns   lined  (older netlist, ~75 cells fewer)

Skew does not order the outcome: 4.077 renders perfectly while 4.389 is lined,
and the other clean placement sits *above* the lined one.  So the lead recorded
in entry 59 is weakened, not confirmed, and entry 55's withdrawal of the skew
theory survives this measurement.

Two readings are consistent with the numbers and only one experiment separates
them.  Either skew is not the discriminator and seed 17's perfection has some
other cause, or there is a threshold somewhere below ~4.2 ns that seed 17 clears
and both 4.389 and 4.657 miss.  The prediction differs: a threshold means
**seed 19 is lined**, a cause unrelated to `clk` skew means it is perfect.

Seed 19's bitstream is therefore built and kept as the discriminator:
`build/clock-monitor/desktop.aa6b0f9d733b.bin`, 4,463,286 bytes, packed from
the same routed netlist the skew above was measured on.  It must be tested on
the board after the seed-17 stability run, not during it, so the two results are
not confounded.
