Admitting table 38's sources does not add a cross-tile wire -- and the reason why

Tested 2026-10-10.  Base: apicula fork `4281068`, chipdb `57a1c2a5...`
(850,124 bytes).  Result: **NEGATIVE**, reverted; the toolchain is byte-identical
to where it started, source clean and the chipdb restored to `57a1c2a5`.

## What was tried

The lead came from two places that turned out to be one.  Entry 56 measured that
the vendor's own `.fse` carries 1,672 and 1,259 distinct named `(dest, src)`
pairs in **table 38** at tiles `(54,88)` (ttyp 80) and `(54,93)` (ttyp 85), where
the model's `clock_pips` holds only 943 and 823 -- about 1,400 pairs missing at
the clock distribution's hub.  And `tools/chipdb-hclk-trace.py` showed that the
divider's network input, `HCLK_MUX_GAMMA30` -- the input the vendor's bitstream
selects and ours does not -- is fed from **another tile**,
`HCLK_MUX_EPSILON30` at `(0,0)`, which is **a destination nowhere**: the
cross-tile wire with no driver.

`fse_clock_pips_138` already reads table 38, but only lets through the *measured*
CLKDIV escape wires (`gw5_hclk_clk_wire_ids`); every other source in the
`105..128` ("unknown wires") and `164..236` ("longwires") spans is discarded.
The experiment removed that restriction for table 38, admitting every table-38
source at those cells.

## The measurement

The chipdb grew, so the change did something -- 850,124 to 855,660 bytes,
`e4937467...` -- but the gate did not move at all:

```
                     spanning   UNDRIVEN   dead-end
  baseline               132        236        316
  table 38 admitted      132        236        316
```

`tools/chipdb-hclk-gaps.py` is the gate because `hclk-bridge-experiment.txt`
established that a change which does not raise **spanning** cannot change any
route, and that reading held here.

## Why, and this is the useful part

The bridge cells **`(54,88)` and `(54,93)` are not keys in `hclk_pips` at all**,
before or after the change:

```
OLD: hclk_pips tiles=171  (54,88) present=False  (54,93) present=False
NEW: hclk_pips tiles=171  (54,88) present=False  (54,93) present=False
```

So table 38's rows never join the clock-plane graph the router sees.  That
reframes entry 56's number: the ~1,400 pairs are not connections *missing from*
the network -- they belong to cells the model does not treat as clock tiles in
the first place.  Adding more of them cannot help, which is why the gate was
flat, and it is the same shape of answer the bridge-cell experiment got.

## What this means for the next attempt

The fix is not "admit more sources"; it is **make the central clock mux part of
the clock network**.  Concretely, the bridge cells have to become clock tiles
whose pips are in `hclk_pips`, and the EPSILON/GAMMA chain has to be joined to
the spine -- the database's own `spine_select_wires` puts SPINE17-23 at rows
27/81, **columns 92-94 (x~93)**, which is the same column as the two bridge
cells, so the spine and the hub are already co-located in the data.  Until
`HCLK_MUX_EPSILON30` has a driver reaching it from the spine,
`HCLK_MUX_GAMMA30` has no network feed and nextpnr must keep taking the fabric
entry `L2HCLK` for the TMDS bit clock.

Also known and not re-derived here: HCLK blocks 0 `(27,0)` and 1 `(27,181)` have
no modelled clock escape at all (the fork's own note, P1.T08c/d).

## Limits

The gate is a pair of counts, and spanning is a *necessary* condition for a
cross-tile route and not a sufficient one, so a flat spanning count proves only
that this change did not add a cross-tile wire -- it does not by itself prove a
future change that does raise it would route.  No routing was run and no board
was involved; the change was not kept, so no bitstream was built from it.

## Correction, same day: the first reading used the wrong graph

The gate above is `tools/chipdb-hclk-gaps.py`, and it reads **`hclk_pips` only**.
But `fse_clock_pips_138` fills **`clock_pips`** -- a different field, and
`himbaechel/uarch/gowin/gowin_arch_gen.py` reads *both* into the routing graph
(`clock_pips` at line 916, `hclk_pips` at 930).  A change inside
`fse_clock_pips_138` therefore **cannot** move the `hclk_pips` counts, and the
flat 132/236/316 above showed only that.  The conclusion happened to be right;
the evidence for it was not.

Re-measured on the graph the change actually feeds, `clock_pips`, dumping every
tile's matrix and counting wire names and cross-tile names:

```
                        dest-entries   names   cross-tile names
  baseline                    484        474            49
  table 38 admitted           484        531            49
```

So the change adds **57 new wire names** to the clock-mux graph and **no new
cross-tile connection at all** -- the same verdict as the `hclk_pips` counts, now
measured where it counts.  The conclusion stands: admitting table 38's sources
does not make the clock hub reachable.

## What the re-measurement turned up on the way, which is the useful part

- **The model's two clock graphs share exactly one wire name, and it is `VCC`.**
  `hclk_pips` carries 876 names, `clock_pips` 531, with **875** hclk-only and
  **530** clock-only.  They are drawn from different name tables, so by name they
  are disjoint.  The join between the HCLK plane and the clock network is a
  **node** statement, not a name one -- `gw5_make_hclk_to_clk_nodes`, driven by
  the measured `_gw5a_hclk_to_clk` map of block/lane to clock-network wire id.
  Anything that tries to join them by adding names to one graph cannot work.
- **`HCLK_MUX_EPSILON30` is an `hclk_pips` name only.**  It is absent from
  `clock_pips` entirely, so its missing driver has to be supplied inside the HCLK
  plane, not by admitting clock-mux rows.

## State

Reverted again and verified: source clean at `4281068`, chipdb back to
`57a1c2a5...` at 850,124 bytes.  No board action; no bitstream built.

## Limits

Unchanged from above, plus this one: the counts are of *names* in two matrices,
and a name shared between tiles is necessary but not sufficient for a routable
path, so a flat cross-tile count rules this change out without licensing the
opposite inference for any other change.
